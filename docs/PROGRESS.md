## 1. 这一轮做了什么

题面最低要求是「在给定工作目录里完成两个任务」。但真实的文件助理不会只面对
一个 32 文件的干净目录 —— 它要面对几百个 PDF、Excel、Word 混在一起的真实资料夹。
所以这一轮的主线是**让它能吃下任意文件夹**。

### 1.1 检索子系统 `agent/index/`（新增，1,593 行）

| 文件 | 行数 | 职责 | 关键判断 |
|---|---|---|---|
| `store.py` | 613 | SQLite FTS5 双索引 + 子串兜底 + RRF 融合 | 不用向量库：零外部依赖、可解释、精确串更强 |
| `parsers.py` | 468 | pdf/docx/xlsx/pptx/csv/md/html/代码 → 结构化块 | PDF 用 pypdfium2 而非 pypdf（快 27 倍）；编码依次试 utf-8/gb18030/big5 |
| `indexer.py` | 204 | 三级增量同步 | `mtime+size` → `sha256` → 重解析，逐级变贵 |
| `chunker.py` | 169 | 结构感知切块 | 不跨标题、表格带表头、**每块带面包屑** |
| `verify.py` | 124 | 命中新鲜度复核 | 索引是快照，会陈旧 —— 这是加索引**引入的新风险** |

三个我认为最值得讲的设计点：

**① 中文检索有一个两条 FTS 路都盖不住的盲区。**
`trigram` 需要 ≥3 字符才能构成三元组；`unicode61` 会把相邻汉字合并成一个 token
（「超出预算」整体是一个词）。结果是「预算」「合同」「发票」「采购」这类
**中文里最常用的双字词，两条路都搜不到**。所以加了第三条 LIKE 子串路兜底。
这不是优化，是正确性补丁。

**② 面包屑是投入产出比最高的一招。**
每个块前置 `财务/2025Q4预算.xlsx > Sheet: 部门明细 > 表头: 部门|预算|实际`。
没有这一行，「研发部 | 1200000」根本无法判断是预算还是实际。
面包屑本身也进索引，命中标题比命中正文更能说明相关性。

**③ 加索引不是纯收益。**
索引是快照，源文件随时会变。模型可能拿着失效的数字回答 ——
这比搜不到严重得多，因为它输出的是**一个看起来有出处的错误答案**。
所以每条命中进上下文前都复核内容哈希，过期的剔除，
并把「剔了什么、为什么」明确告诉模型，而不是静默丢弃。

### 1.2 只读边界（新增）

`ask` 模式下 agent **完全没有写能力**：`write_file` / `move_file` 不进工具清单，
`Sandbox(read_only=True)` 再做一层兜底断言。

起因是一次真实事故（§4.4）。现在的分工是：**agent 只读，落盘由操作者用 `--out` 决定**，
写盘动作发生在 agent 之外 —— 所以无论语料里埋了什么诱导，都写不进你的资料目录。

### 1.3 CLI 扩展

## 2. 实测数据（都是真跑出来的，不是估算）

### 索引性能

| 语料 | 规模 | 首次索引 | 增量（无变更） | 检索延迟 |
|---|---|---|---|---|
| `workspace_seed/` | 32 文件 → 1,262 块 | 0.44s | **0.005s** | < 1ms |
| 真实 PDF 语料 | 39 文件 / 37MB / 8 个 PDF → 673 块 | 10.4s | **0.002s** | 0–5ms |

增量那一栏是关键：没有它，「每次提问前同步一下」根本不成立。

### PDF 解析器换型

| 库 | 174 页耗时 | 抽出文本量 | 许可证 |
|---|---|---|---|
| pypdf | 283.5s | 较少 | BSD |
| **pypdfium2** | **10.3s（27×）** | 更多 | Apache-2.0 / BSD |
| PyMuPDF | 快 | 多 | **AGPL —— 商用要买授权，直接排除** |

整体索引时间因此从 304.7s 降到 12.4s。**性能问题先量出来再改**，
不量的话很容易去优化根本不是瓶颈的地方。

### 中文检索召回（对照 SQL 原文真值）

在真实语料上，对每个词同时做「SQL LIKE 数原文有多少块」和「走完整检索返回多少」：

| 查询 | 原文实际存在 | 检索返回 | 走哪条路 |
|---|---|---|---|
| 设备 | 15 块 | 10（limit=10，全部含字面词） | word + substr |
| 超时 | 有 | 10 | word + substr |
| 状态 | 有 | 10 | substr |
| timeout | 18 块 | 10 | word + gram |
| 服务器 / 发票 | **0** | **0** | — |

最后一行同样重要：**语料里没有的词必须零命中**。兜底路不能把召回换成噪声。

## 4. 这一轮发现并修掉的 bug（含根因）

写在这里不是自我检讨，是因为**每一个都对应一条现在锁住它的测试**，
面试时这部分比功能清单更能说明问题。

### 4.1 短文件整篇消失（最阴险）

`MIN_CHUNK_CHARS = 24` 本意是滤掉「第 3 页」「---」这类噪声碎片。
但一个总长 22 字符的文件，唯一的块被丢弃 → **文件在索引里彻底不存在**，
全程零报错。用户搜不到，也永远查不出为什么。

而「搜不到」会被直接理解成「不存在」—— 于是索引开始生产错误结论。

**根因**：把「噪声过滤」和「内容保全」放在同一个阈值上判断。
对检索索引，假阴性远比噪声昂贵：噪声块 BM25 分低会自然沉底，
漏掉的内容没有任何补救路径。

**修复**：阈值降到 8，并在 `chunk_document` 结尾加兜底 ——
非空文档至少产出一个块。
锁死于 `test_short_file_is_never_silently_dropped`、`test_single_chunk_document_survives`。

### 4.2 块重叠破坏了标题边界（我自己引入的设计冲突）

为防止答案正好落在切口上，相邻块之间加了重叠。但实现时无差别地
把上一块尾部拼进下一块，**直接违反了「永不跨越标题边界」这条更重要的规则** ——
检索到那样的块，模型会以为两个章节的内容属于同一上下文。

**根因**：两条规则各自看都对，相遇时没定优先级。

**修复**：只在同一章节（面包屑相同）内重叠。边界规则优先。
锁死于 `test_chunker_never_crosses_headings`。

### 4.3 子串兜底是「全有全无」，导致静默漏召回

兜底路原本写成 `if not rankings`（前两路全空才跑）。真实语料实测：
「设备」存在于 5 个块，`word` 路恰好命中 2 个（那两处前后是空格，
token 边界对上了），于是兜底不再触发，**另外 3 个被永久漏掉**。

最危险的地方是：**它返回了结果**。空结果会让人怀疑，
返回了一半的结果不会。

**根因**：把兜底当降级方案，而不是当一条独立召回路。

**修复**：三路平权，一律参与 RRF 融合。
锁死于 `test_substring_path_runs_even_when_word_path_hits`。

### 4.4 `ask` 对用户语料有写权限（最严重）

`ask --label X` 直接把索引根当工作目录，于是 agent 把自己生成的答案
**写进了被索引的语料目录**。下一次检索时，那份自产文件排到命中第一名 ——
自我引用回路。

换成你的公司文档，后果不是脏数据，是 **AI 静默修改了正式文件**。

**根因**：把「检索范围」和「工作目录」当成了同一个概念。它们不是。

**修复**：`ask` 全程只读，写工具不进工具清单；`--out` 由 CLI 落盘。
锁死于 `test_read_only_blocks_write_and_move`、
`test_read_only_mode_hides_write_tools_from_model`。

## 6. 已知限制与后续要排查的点

### 6.1 部署相关（**最需要你留意**）

| 问题 | 说明 | 怎么办 |
|---|---|---|
| **线上还是旧代码** | 这一轮的改动都在本地，Railway 上跑的是上一次部署的版本 | push 之后 Railway 会自动重新构建；部署完自己开一次页面确认 |
| **Railway 文件系统是临时的** | 容器重启/重新部署后 `.index/index.db` **会丢**，需要重新 sync | 演示前现场 sync 一次即可（种子语料只要 0.44s）；要持久化得挂 Railway Volume |
| **Web 端注册的是「服务器上的路径」** | 远程用户在网页里填 `D:/公司资料` 一定失败 —— 那是**你**电脑上的路径，服务器看不到 | 线上演示只注册容器内路径（如 `workspace_seed`）；「索引我自己的文件夹」这个能力请用本地 CLI 演示 |
| 无文件上传 | 网页上没法把本地文件传上去建索引 | 属于下一步功能，不是 bug |

### 6.2 功能限制

| 限制 | 影响 | 备注 |
|---|---|---|
| 检索无语义泛化 | 搜「采购」召不回「购买」 | 词法检索的固有代价；RRF 框架已就位，要补就再加一路 embedding |
| `substr` 路是全表扫描 | 十万块级别会到百毫秒 | 当前体量无感；真要扩容需换中文分词或 n-gram 倒排 |
| 索引要手动 `sync` | 改了文件不同步就查不到新内容 | 但**陈旧证据会被复核剔除**，不会因此给出错误答案 |
| Web 模式下证据只有块、读不到全文 | 网页里 agent 的 `read_file` 只能看会话工作区，看不到索引目录原文 | 这是刻意的隔离；要核对全文请用 CLI `ask` |
| 单机 SQLite | 多实例无法共享索引 | 要扩就换 Postgres + pg_trgm |
| 无并行工具调用 | 多文件读取串行，慢 | 早就在已知不足清单里 |
| 无产物自检回路 | 写完索引不会自己复核每条是否成立 | **我认为这是最该补的一件事** |

### 6.3 如果出问题，先看这里

| 症状 | 大概率原因 | 处理 |
|---|---|---|
| `index sync` 报某些文件失败 | 缺解析依赖，或文件本身损坏/加密 | `index status` 会列出失败文件与原因；缺依赖就装 `requirements.txt` |
| 中文搜不到 | 先用 `index search` 直接查，绕开模型 | 若 `search` 有结果而 `ask` 说没有，是模型环节；反之是索引环节 |
| 搜出来的内容和文件对不上 | 索引陈旧 | 跑 `index sync`；系统本身也会复核并剔除过期证据 |
| 结局是 `DEGRADED` | 步数或 token 触顶 | **不等于失败**，已落盘产物全部保留；可调 `AGENT_MAX_STEPS` / `AGENT_TOKEN_BUDGET` |
| pip 装依赖报 UnicodeDecodeError | `requirements.txt` 混入了非 ASCII 字符 | 该文件必须保持纯 ASCII（Windows 下 pip 用 GBK 读它） |
| 线上 Demo 报未授权 | 访问口令 | 在 Railway 环境变量里看 `DEMO_ACCESS_CODE` |

## 8. 面试时值得主动讲的三点

不要只讲「我实现了什么」，讲**为什么这么选**。

1. **最强的安全边界是「能力不存在」。**
   工具集里没有删除能力，工作区里两处注入都要求删文件 ——
   无论模型被说服到什么程度，攻击都不可能成功。
   只读模式是同一条思路的延伸：模型调用不了一个它看不见的工具。

2. **用接口形状引导模型，而不是用提示词哀求。**
   `read_file` 的签名里没有「读全文」这个选项；`search` 的返回体大小
   与被搜文件大小无关。面对 12,000 行日志，模型自己就转向了 `search`。
   *提示词会在上下文压力下被忽略，接口不会。*

3. **加索引引入了新风险，不是纯收益。**
   索引是快照，会陈旧，会让模型输出「看起来有出处的错误答案」。
   所以每条证据进上下文前都要复核哈希。
   能主动说出「我引入的这个方案带来了什么新问题、我怎么处理的」，
   比多写三个功能有用。
